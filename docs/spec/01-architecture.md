# 01. Архитектура Fervo TV

Собственное решение Fervo TV. Исходная точка — текущий одномодульный `app` (см. `docs/ARCHITECTURE.md`):
состояние в Compose, источник в `SharedPreferences`, кэш плейлиста в `playlist.tsv`. Ниже — во что он
превращается и какие требования к ядру выдвигают разделы 10–32.

## 1. Модули

Один репозиторий, один Gradle-проект, три модуля (+ один необязательный):

```
core/            Android-библиотека без UI: модели, источники, парсеры, синхронизация, БД, EPG,
                 движки воспроизведения, слой команд ввода, настройки и Defaults
app-tv/          приложение для Android TV: Compose for TV, навигация пультом, leanback-лаунчер
app-mobile/      приложение для телефонов и планшетов: Compose (Material 3), сенсор
engine-mpv/      необязательно: альтернативный движок на libmpv (подключается флагом сборки)
```

Правила зависимостей:
- `app-tv` и `app-mobile` зависят от `core`, друг от друга — нет.
- `core` не зависит от Compose и от `app-*`. Всё, что нужно экранам, `core` отдаёт как `Flow`/`PagingData`
  и suspend-функции.
- `engine-mpv` зависит от `core` (реализует его интерфейс движка). `core` о нём не знает: движки
  регистрируются при старте приложения.
- Чистая логика (парсеры, нормализация названий, сопоставление EPG, правила расписаний, расчёт
  подложки логотипа по пикселям, шифрование копии) пишется без Android-классов, чтобы проверяться
  JVM-тестами. Где Android-класс нужен (база, `XmlPullParser`, `KeyEvent`), он изолирован тонким
  адаптером.
- Небольшие общие Compose-элементы (логотип канала с подложкой) пока живут в каждом приложении. Если
  дублирование вырастет, допустим модуль `ui-common`; заранее его не заводим.

Один APK на всё (как сейчас) сохраняется до конца P0: `app-tv` получает leanback-лаунчер и
`touchscreen required=false`, `app-mobile` — обычный лаунчер. Пакеты и подписи — отдельное решение
владельца при выпуске.

## 2. Что переносится из текущего кода в `core`

| Сейчас (`app`) | В `core` | Изменения |
|---|---|---|
| `Model.kt` | `model/` | Модели расширяются (VOD, эпизоды, передачи, профили); `Source` получает тип Stalker |
| `M3uParser.kt` | `source/m3u/` | Разбор из `Reader` построчно с выдачей записей по одной (callback/`Sequence`), а не `List` из строки. Новые атрибуты: `tvg-chno`, `catchup*`, `url-tvg`/`x-tvg-url`, `type`, `#EXTVLCOPT`, `#KODIPROP`. Существующие тесты сохраняются |
| `Xtream.kt` | `source/xtream/` | Потоковый разбор JSON; добавляются VOD, сериалы, EPG, информация об аккаунте |
| `Repository.kt` (`httpGet`, хранение источника) | `net/`, `source/` | Единый HTTP-клиент: User-Agent/Referer на источник и на поток, редиректы http↔https, таймауты из Defaults, пользовательский DNS (SET-008) |
| `PlaylistCache.kt` | БД | Кэш заменяется базой. При первом запуске новой версии `playlist.tsv` импортируется в БД и удаляется |
| `LogoIndex.kt` | `logos/` | Без изменений поведения; результат совпадений хранится в БД рядом с каналами |
| `Input.kt` (`Action`) | `input/` | Перечень команд расширяется (цифры, Last, цветные клавиши, долгие нажатия); сопоставление клавиш и жестов — в `core`, экраны работают только с командами |
| `Defaults.kt` | `core/Defaults.kt` | Остаётся единственным местом значений по умолчанию для обоих приложений |
| Подбор подложки логотипа (`ui/ChannelLogo.kt`) | `logos/` | Расчёт цвета по пикселям — чистая функция в `core`; отрисовка — в приложениях |

## 3. Данные

### 3.1 Локальная база

- SQLite через Room. Одна база на устройство; данные профилей разделены столбцом профиля.
- Основные сущности: источник, категория, канал, фильм, сериал, сезон/эпизод, канал телегида,
  передача, сопоставление канал↔телегид, избранное, история/позиции, пользовательские правки
  (скрытие, переименование, порядок, подборки), профиль, задания записи и загрузки, напоминания.
- **Поиск** — полнотекстовый индекс (FTS4) по названиям каналов, фильмов, сериалов и передач,
  с префиксным совпадением слов (см. HOME-010). Нормализация текста (регистр, ё→е, разделители)
  одинаковая для индекса и запроса.
- **Постраничная выдача** — Paging 3 для всех длинных списков (каналы категории, постеры, результаты
  поиска, строки сетки телегида по видимому окну времени). Экран никогда не загружает весь каталог.
- **Масштаб:** запись импорта — пакетами в транзакциях; индексы по (источник, категория, порядок),
  (источник, внешний ID), (канал телегида, начало). Целевые ориентиры на приставке среднего класса:
  открытие категории из 5 000 каналов < 300 мс до первого экрана, поиск по 200 000 названий < 200 мс,
  импорт 50 000 каналов + 150 000 фильмов без OOM при куче 256 МБ.
- **Обновление без потерь:** синхронизация сопоставляет элементы по устойчивому ключу (источник +
  ID провайдера, для M3U — URL потока, при его отсутствии — название+группа). Пользовательские данные
  (избранное, история, правки, сопоставления EPG) привязаны к ключу и переживают пересинхронизацию.
- **Миграции** схемы обязательны и покрыты тестами; повреждённая база не стирается молча — пользователь
  видит экран «Повторить / Сбросить данные».

### 3.2 Настройки

Настройки — типизированное хранилище (DataStore) с дефолтами из `Defaults.kt`. Уровни: общие →
профиль → источник (переопределения, SET-010). Чтение настройки всегда возвращает итоговое значение
с учётом уровней.

### 3.3 Секреты

Пароли источников, MAC и идентификаторы порталов, ключи сервисов хранятся в зашифрованном хранилище
(Android Keystore). Автоматическая системная резервная копия отключена (см. BAK-008).

## 4. Потоковый разбор источников

| Формат | Как читается |
|---|---|
| M3U/M3U8 | Построчно из `Reader` (поддержка BOM, CRLF), запись в БД пакетами по мере чтения |
| Xtream JSON | Потоковый JSON-ридер по массиву: элемент за элементом, без построения дерева всего ответа |
| XMLTV | Потоковый XML pull-парсер; вход может быть `.gz` (распознаётся по сигнатуре, а не по расширению); сохраняются только передачи каналов, которые есть в плейлистах, и только в пределах окна хранения (EPG-003) |
| Stalker | Постраничные запросы портала, каждая страница пишется сразу |

Требования: память на импорт не растёт с размером источника; ошибка в одной записи пропускает эту
запись, а не весь файл; прогресс (прочитано записей/байт) доступен экранам; импорт отменяем.

## 5. Синхронизация и фоновые задачи

- WorkManager: обновление источников и телегидов по расписанию каждого (SRC-005, EPG-001), подбор
  логотипов, метаданных и спортивных данных, загрузки и записи (как foreground-службы с уведомлением).
- Всё фоновое имеет единое состояние «что сейчас делается», которое показывает индикатор UI-015.
- Первый импорт может продолжаться в фоне, пока пользователь уже смотрит (SRC-016).
- Сначала кэш: экраны подписаны на БД, поэтому новые данные появляются без перезапуска экранов и без
  сброса фокуса, прокрутки и фильтров.

## 6. Воспроизведение

### 6.1 Интерфейс движка

`core` объявляет интерфейс движка: подготовить элемент (URL, заголовки, DRM, тип контейнера, позиция),
управление (play/pause/seek/скорость/громкость), дорожки (аудио, субтитры, видео-качества), события
(состояние, ошибка с категорией, статистика потока). Экраны работают с интерфейсом, а не с ExoPlayer
напрямую. У каждого движка — список возможностей (DRM, passthrough, типы субтитров), по которому
выбирается подходящий.

### 6.2 Цепочка запасных вариантов

1. **Media3 ExoPlayer** — по умолчанию для эфира и видеотеки; единственный для DRM.
2. **ExoPlayer с FFmpeg-аудиодекодером** — когда звук в формате, который устройство не декодирует
   (AC3/E-AC3/DTS/TrueHD и т. п.), или по настройке PLR-012.
3. **libmpv** (`engine-mpv`, если включён в сборку) — когда предыдущие не открыли поток.

Внутри движка перебираются варианты формата (HLS ↔ MPEG-TS, переопределение контейнера по ответу
сервера). Каждый шаг пробуется один раз, весь перебор ограничен временем «сдаться через» (PLR-005).
Порядок движков настраивается для эфира и видеотеки отдельно (PLR-018), выбор для канала запоминается
(PLR-017).

### 6.3 Сеанс воспроизведения

Один сеанс плеера живёт выше экранов: превью в списке, полноэкранный режим, плеер в углу и
фоновое прослушивание — это разные представления одного сеанса, поэтому переход между ними не
перезапускает поток. MediaSession подключается к сеансу.

## 7. Ввод

Слой команд остаётся главным принципом: клавиши пульта, клавиатура, геймпад и жесты переводятся в
команды `core/input`; экраны обрабатывают команды. Переназначение клавиш (UI-013) — таблица
«клавиша/долгое нажатие → команда» в настройках.

## 8. Тесты

- JVM unit-тесты на всё в `core`, что не требует Android: парсеры M3U/Xtream/XMLTV/Stalker (включая
  большие синтетические файлы для проверки памяти), нормализация названий, сопоставление EPG,
  разбор сезонов/эпизодов, расписание напоминаний и записей, слияние при восстановлении, шифрование
  копии, порядок запасных движков.
- Instrumented-тесты на БД: миграции, FTS-поиск, постраничная выдача на 200 000 строк.
- Текущие 13 тестов переносятся в `core` и продолжают проходить. CI запускает тесты всех модулей.

## 9. Основа для других платформ

Tizen, webOS и Linux не обязаны использовать Kotlin-код ядра. Общим для всех клиентов является:
- **поведение** — разделы 10–32 этой спецификации;
- **форматы данных** — правила разбора M3U/Xtream/XMLTV/Stalker, нормализация названий, формат файла
  резервной копии (BAK-001) и протокол переноса по локальной сети (BAK-006), чтобы данные свободно
  переходили между устройствами разных платформ.

Поэтому эти правила описываются в `core` явно (тесты как исполняемая документация), а форматы обмена —
версионируются. Перенос самого ядра на Kotlin Multiplatform — отдельное решение после P6.
